# LLM Agents and Tool Use: A Research Survey

## TL;DR

LLM tool use is not merely a model emitting a syntactically valid function call. A capable agent must choose a tool, construct arguments, interpret returned observations, maintain relevant state, sequence actions toward an objective, and know when to stop or seek clarification. The literature spans prompted reasoning–action loops such as ReAct, learned tool-use behavior such as Toolformer, structured function-calling models, and orchestration layers that retrieve APIs, plan, search, and reflect. These are complementary system and training choices rather than a settled hierarchy of universally superior architectures. [1][2][3]

Empirical progress is real but difficult to compare: results depend on tool pools, prompts, task distributions, execution environments, and scoring protocols. Research has therefore expanded from isolated call correctness toward stateful and multi-turn task completion, instruction adherence, and trajectory-level reliability. [4][5][6] Security is a first-order design issue because prompt injection can turn otherwise useful tool access into data disclosure or harmful action; least privilege, constrained interfaces, independent policy checks, and approval gates should be enforced around the model rather than entrusted to its discretion alone. [7][8][9]

## Background

An LLM agent can be treated as a language model embedded in an interaction loop: it receives an objective and tool affordances, emits a decision or action, observes the environment's response, and continues. The environment may be a search API, code interpreter, database, browser, business application, or simulated task world. Agent surveys organize these systems using dimensions such as tool use, planning, feedback, roles for policy/evaluation, and interaction workflows. [3][5]

Three distinctions help clarify the field. First, **tool interface** is different from **agent control**: a function-calling format specifies a structured action and arguments, while a planner or loop determines which calls to make and how to use their results. Second, **tool use** differs from **retrieval-augmented generation** in emphasis: both bring external information into generation, but an agent may issue state-changing actions, chain tools, and adapt based on execution feedback. Third, **model capability** is not the same as **system reliability**: execution permissions, state management, retries, result validation, and policy enforcement substantially shape outcomes. These distinctions are reflected in the reviewed taxonomies and benchmarks. [3][10][4][5]

The evidence reviewed here includes foundational arXiv papers, papers surfaced through Hugging Face Papers search, and OWASP guidance. The results and numerical comparisons below are author-reported and benchmark-specific; they should not be read as a unified leaderboard. Several papers propose methods or evaluation frameworks, and proposals are distinguished from demonstrated deployment effects.

## Theme 1: Agent architectures—from action loops to orchestration

**Interleaving reasoning, action, and observation.** ReAct prompts a model to alternate natural-language reasoning with task-specific actions, then use external observations to decide what to do next. In its reported experiments, the approach improved over action-only prompting on knowledge and interactive tasks; on ALFWorld, its best reported trial reached 71% success versus 45% for the best Act-only trial. The authors also identify few-shot context limits and difficulty learning complex behaviors from a small number of demonstrations. [1] This is evidence that feedback can help in tested settings, not proof that a specific reasoning trace is necessary in every agent.

Indeed, a later prompt-sensitivity analysis on selected sequential decision tasks found that performance was minimally affected by interleaving reasoning and action or by the generated reasoning content, and instead tracked similarity between demonstrations and test queries. It cautions that exemplar selection may account for apparent gains in those settings. This qualifies, rather than erases, the original task-specific ReAct results. [11]

**Structured function calling and learned tool policies.** Function calling provides a machine-readable interface for selecting functions and populating arguments. It is not, by itself, a planning algorithm or complete agent loop. Toolformer trains a model to choose an API, determine when to call it, formulate arguments, and incorporate the result into subsequent predictions; its self-supervised procedure selects candidate calls based on whether they improve prediction of future tokens. [2] GRANITE-20B-FUNCTIONCALLING frames the skill more broadly as multiple subtasks—including function-name and parameter-value detection, chaining, parallel calls, next-best-function prediction, and response generation. [10] ToolACE uses a large API pool and verified synthetic dialogue generation to train function-calling models. [12] Together, these works illustrate how tool-use competence can be learned or decomposed, while leaving orchestration and environment safeguards as separate system responsibilities.

**Planning, search, and hierarchy.** When the action space is large, systems add components around the model. ToolLLM combines API retrieval, ToolBench data, and depth-first search over candidate call paths; its benchmark includes 16,464 REST APIs across 49 categories. [13] AnyTool uses hierarchical API retrieval, a solver, and self-reflection, reporting higher average pass rates than ToolLLM under its revised ToolBench evaluation protocol. [14] ToolChain* models tool sequences as a decision tree and applies A* search to prune branches, reporting performance and runtime gains on its own experiments. [15] GoalAct combines a continuously updated global plan with hierarchical execution and reports improvements on LegalAgentBench. [16] NaviAgent proposes graph-driven bilevel planning to select an interaction mode and construct toolchains as APIs evolve. [17]

These designs target different failure modes—finding a relevant API, avoiding poor sequences, or maintaining a global objective—and their headline scores are not directly comparable across different tasks and metrics. A practical design choice is therefore to match orchestration complexity to the task: a direct, well-constrained function call may not require search, whereas open-ended multi-step work can benefit from retrieval, dependency modeling, or replanning. This is a synthesis of the architectures, not a controlled finding that one pattern is optimal. [13][14][15][16][17]

## Theme 2: Training tool-use competence

Training methods range from prompting a general model with tool descriptions, to supervised fine-tuning on tool-call demonstrations, to reward-driven interaction. A survey treats these as complementary paradigms that production systems may combine, and notes that tool use, planning, and feedback learning solve related but distinct problems. [3]

Toolformer demonstrates a self-supervised alternative to relying only on hand-authored trajectories: it samples candidate API calls and retains calls that improve prediction of subsequent text. [2] ToolACE addresses data generation through multi-agent synthesis and rule- and model-based verification, while the Granite work uses a multi-task curriculum over distinct function-calling behaviors. [10][12] These efforts suggest data needs to cover not only call syntax, but tool selection, argument construction, sequencing, parallelization, and post-call responses. [10][12]

A remaining difficulty is learning from interaction when successful trajectories are scarce or rewards are delayed. A 2025 proposal, Environment Tuning, argues that synthetic-data supervised fine-tuning can overfit and standard reinforcement learning can face cold-start and stability challenges; it proposes learning directly from problem instances without pre-collected expert trajectories. [18] This is a proposed training direction, not settled evidence that it outperforms conventional SFT or RL broadly. More generally, long tool chains raise credit-assignment questions: a task can fail because of an early tool choice, a malformed argument, an execution problem, or an incorrect interpretation of a later result. [3][5]

## Theme 3: Evaluation—calls, instructions, state, and task success

A benchmark that checks whether the model emits a valid call measures only part of the system. The agent evaluation survey distinguishes capabilities and reliability and describes measures for tool selection, planning, call order, dependency handling, and memory. [5] ToolSandbox explicitly tests stateful execution, implicit dependencies across tools, and conversational interaction with a user simulator; it scores intermediate and final milestones and reports that state dependency, canonicalization, and insufficient information remain challenging. [4] This helps expose failures that stateless, single-turn function-call tests can miss.

Format and instruction adherence also matter. IFEval-FC focuses on parameter-description instructions—such as quoting values or formatting dates—that the authors say prior function-calling evaluations do not adequately capture. [6] Granite's multi-task setup likewise highlights that correct function names, values, chains, and parallel invocations are separable capabilities. [10] In deployed systems, a syntactically valid call that violates a parameter constraint can still produce an incorrect or unsafe action.

Task-level success is important, but benchmark protocols can distort it. AnyTool reports that an earlier ToolBench evaluation protocol could yield artificially high pass rates and introduces AnyToolBench to address the issue. [14] Thus, claims of superiority should be interpreted alongside how tools are simulated, what counts as success, whether state persists, how invalid calls are handled, and whether the evaluator independently verifies execution. ToolSandbox and the agent-evaluation survey provide evidence for broadening evaluation to trajectories, state, reliability, and memory—not just isolated call accuracy. [14][4][5]

## Theme 4: Safety, security, and control of tool authority

Tools expand what an agent can do and what information it can reach. OWASP identifies excessive agency as arising from excessive tool functionality, permissions, or autonomy, with prompt injection, hallucinations, compromised tools, or peer agents as possible triggers. The resulting harms can affect confidentiality, integrity, or availability. Its recommendations include narrowly scoped tools and schemas, least-privilege permissions, execution in the user's authorization context, human approval for high-impact actions, and independent policy enforcement. These are security recommendations, not controlled proof that any one mitigation works in all systems. [7]

Empirical prompt-injection research illustrates the stakes. In a banking-agent study using AgentDojo tasks and an expanded synthetic dataset, attacks had roughly 20% average success over 16 tasks and roughly 15% over an expanded 48-task evaluation; the authors found that existing built-in defenses did not fully prevent personal-data leakage in the expanded evaluation. The tested models could avoid revealing passwords yet still disclose other personal information. These figures describe the study's attack setup and should not be generalized to all deployments. [9]

CaMeL explores an architectural defense: separate trusted control flow from untrusted content, track data provenance/capabilities, and check policies when tool calls are made. The paper reports provable security on 77% of AgentDojo tasks versus 84% for an undefended system, indicating a security–utility trade-off in that benchmark. [8] Combined with OWASP's recommendations, this supports a defense-in-depth principle: use the model for task reasoning, but place permission boundaries, data-flow controls, action validation, and approval requirements in independently enforced system components. [7][8][9]

## Trends and open problems

1. **From calls to workflows.** The field's center of gravity is shifting from whether a single call is correct toward whether a sequence is executable, state-consistent, and successful end to end. ToolSandbox's stateful tasks and hierarchical/search-based systems address parts of this challenge, but long-horizon performance still depends on reliable intermediate results and recovery from errors. [14][15][4][5]
2. **Dynamic tools and robust composition.** Tool pools change, APIs differ in semantics, and multi-tool tasks require correct ordering and transfer of intermediate outputs. Graph-based approaches such as NaviAgent are a response to these orchestration demands, but evidence on robustness to changing real-world APIs remains bounded by the paper's reported evaluations. [13][17]
3. **Better training signals and credit assignment.** Supervised examples can teach interface behavior, while interaction-based training may better expose recovery and adaptation; yet rewards are sparse, trajectories costly, and comparison protocols vary. Environment Tuning exemplifies exploration beyond fixed expert traces, but further controlled comparisons are needed. [3][10][12][18]
4. **Evaluation beyond static benchmarks.** Priorities include persistent state, realistic tool errors, instruction constraints, multi-turn user interaction, unseen APIs, and independent verification of results. Existing sources show that changing the benchmark design changes what is measured; no single score currently captures all relevant dimensions. [14][4][5][6]
5. **Safety as a system property.** Prompt injection and overbroad permissions cannot be solved solely by asking a model to ignore malicious content. The promising pattern in the available evidence is constrained capability plus independent mediation and human oversight for consequential actions; measuring the utility cost and coverage of those controls across varied tasks remains open. [7][8][9]
6. **Open questions.** Important unresolved issues include how to attribute long-horizon failures to individual calls, scale reliable tool discovery without overwhelming models with choices, retain useful state without accumulating irrelevant context, adapt to API changes, and evaluate multi-agent or multimodal tool use under realistic constraints. Surveys and proposed orchestration architectures identify these as research directions, but the sources reviewed here do not establish general solutions. [3][5][17]
